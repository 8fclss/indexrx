## Notes

Hypotheses written before the runs and adjusted after the measurements.

- **01 (confirmed):** I expected the plan to go from `Limit -> Gather Merge -> Sort -> Parallel Seq Scan` to `Limit -> Index Scan` with both conditions in `Index Cond` and no `Sort`, all happened accordingly. Trying different indexes resulted in: 
    - *(user_id)* alone — Bitmap Heap Scan + top-N Sort; ~0.54 ms warm time and 18 MB index size
    - *(created_at, user_id)* — Turned out to be not as bad as I thought initially, but still no `Sort` and fewer buffers. The index is walked backwards by date and checks `user_id` inside the index, so the heap is touched only 20 times, but ~300 index pages are read to find 20 hits.
    - *(user_id, created_at)* — ASC and DESC on created_at actually give the same result and size here: the planner reads the ASC index backwards.
- **02 (partly confirmed):** My hypothesis was that instead of `Seq Scan` (before) I could use a partial index `(status) WHERE status = 'pending'` which would allow for a `Bitmap Heap Scan` with only a few thousand buffers. I expected it to make a 3–5x speedup, wwith index well under 1 MB and no need for `VACUUM`. What turned out to be a better solution is a covering index (`(id) INCLUDE (user_id, total) WHERE ...`) but that was not quite what I had in mind, so at first I ran my own variant:

    | Index | Plan | Buffers | Time, ms (cold / warm) | Size |
    |-------|------|---------|------------------------|------|
    | none | Parallel Seq Scan | 18510 | 32 / 29 | – |
    | `(status) WHERE status = 'pending'` (my hypothesis) | Index Scan | 7730 | 27 / 4.8 | 88 kB |
    | `(id) INCLUDE (user_id, total) WHERE status = 'pending'` + `VACUUM` | Index Only Scan | 52 | 0.89 / 0.75 | 416 kB |

    - **Right:** the `Seq Scan` before, the partial index idea, "a few thousand buffers" (7730), "well under 1 MB" (88 kB), and no `VACUUM` needed for this index.
    - **Wrong node:** I expected `Bitmap Heap Scan`, the planner chose a plain `Index Scan`. Not sure, but if I were to guess: all entries of this index have the same key (`pending`), so they are stored in table order and the scan walks the table pages in order, each once, which makes a plain Index Scan about as cheap as a bitmap.
    - **Time:** warm it was 6x better (29 -> 4.8 ms), but the cold run (27 ms) actually was barely faster than the seq scan (32 ms), because 7.7k scattered pages must be read from disk.
    - **What I missed:** the index does not have to be a lookup structure only. If it also contains the columns the query selects (`INCLUDE`), the table is not touched at all: 7730 -> 52 buffers, ~150x less than my own variant, and ~350x less than the seq scan. The 52 buffers are exactly the whole 416 kB index (52 pages of 8 kB): every entry of a partial index matches the query.
    - **Takeaway:** in my index `status` is the same in every entry, so it adds nothing; the `WHERE` predicate does the filtering. What the indexed columns must do is serve what the query needs.
        - Time reduction has a ceiling: returning 10k rows still costs ~0.5 ms, so in the end buffers show the win more honestly (18510 -> 52, ~350x) than time (29 -> 0.75 ms, ~40x).
        - The estimate was good (`rows=9733` vs 10061 actual) because all four statuses are in the most common values (MCV) list.
    - **Not tested:** what `Index Only Scan` does with a stale visibility map (`VACUUM` was run before the first measurement), and the full index on `status`.
- **03 (mostly confirmed, `ANALYZE` was unexpected):** My hypothesis was a `Seq Scan` (probably without workers) and something like 30-40 ms before; an index on the expression `lower(email)` because a index on `email` would just not fit the query; after it an `Index Scan` with under 10 buffers and under 1 ms; an index of a few MB, smaller than the table; and no need for `ANALYZE`, because the planner would see that only one row matches.
    - **Right:** the expression index, `Index Scan`, 4 buffers instead of 1860, ~0.03 ms instead of 20–33 ms, and the index (7960 kB) is smaller than the table (1860 pages = ~14.5 MB).
    - **Detail I got wrong:** the seq scan is `Parallel` with 1 worker, not a `Seq Scan`. I guess the table is just big enough for the planner to use a worker.
    - **Wrong:** `ANALYZE` matters. Right after `CREATE INDEX` the planner still estimated `rows=1000` and chose `Bitmap Heap Scan` (cost 1657). After `ANALYZE users` the estimate became `rows=1` and the plan became `Index Scan` (cost 8.44). Without statistics on `lower(email)` the planner has no base to estimate on and it uses default guess of 0.5% of the table (1000 rows of 200k); `ANALYZE` is what collects statistics on the indexed expression.
    - In this query the wrong estimate costed nothing: the bitmap plan read the same 4 buffers and took 0.056 ms against 0.038 ms. It would probably matter more when this query is a part of some bigger one (a join, for example) where the row estimate drives the choice of the join method.
    - **Plain index on `email`:** not used, the plan stayed `Parallel Seq Scan` with exactly the same cost (4724.71) and 1860 buffers. The planner does not know that `lower(email)` is related to `email` so the indexed expression has to match the one in the query.
- **04 (mostly confirmed, size was unexpected):** My hypothesis was a `Seq Scan` and 10–20 ms before, because a B-tree cannot search for a substring; a GIN index with `pg_trgm`; after it a `Bitmap Heap Scan` over a `Bitmap Index Scan` with buffers dropping to tens and a time of ~1 ms; an index around the size of the table or larger; and I did not know whether the planner would use the index on such a small table.
    - **Right:** `Seq Scan` with 1860 buffers and 10–13 ms; the `pg_trgm` GIN index; the `Bitmap Heap Scan` plan; and the planner does use the index even on a table this small (cost 99.75 against 4360 for the seq scan).
    - **Plain index on `email`:** not used, the plan stayed a `Seq Scan` with the same cost (4360) and 1860 buffers. A B-tree is sorted from the first character, so it cannot help when the pattern starts with `%`.
    - **Buffers were hundreds, not tens:** 206 instead of 1860 (9x), of which 200 are table pages and 6 are index pages. Time went from 10 ms to 0.43 ms (~24x warm), inside my 10–100x guess.
    - **Why 200 table pages for 20 rows:** the index returned 200 candidate rows (`rows=200` in the `Bitmap Index Scan`) and the recheck threw away 180 (`Rows Removed by Index Recheck: 180`). A trigram index only knows that an email contains the trigrams `999` and `99@`, not that they form `9999@` together. So it also returned the 180 ids that end in `999` but not in `9999`, and each candidate sits on its own table page.
    - **Wrong about the size:** the index (6976 kB) is smaller than the table (15 MB), about 46% of it not equal or larger.
- **05 (mostly confirmed, yet again size was unexpected):** My hypothesis was a `Parallel Seq Scan` under an `Aggregate` (because of `count(*)`) with tens of thousands of buffers, more than `orders`, and a few hundred ms before; a GIN index `gin (payload)`; after it a `Bitmap Heap Scan` with a few thousand buffers and a time ~10x better; the planner using the index without trouble; and a big index, maybe over 100 MB.
    - **Right:** `Finalize Aggregate -> Gather -> Partial Aggregate -> Parallel Seq Scan` with 43603 buffers (the table is 341 MB, so it is the whole table) and 444 ms cold / 136 ms warm; the GIN index; `Bitmap Heap Scan`; 3732 buffers after (~12x fewer); time 26x better cold and 16x warm, even better than my guess; and the planner took the index right away (cost 1103 against 60228).
    - **Wrong about the size:** the index is 24 MB, about 7% of the table, not over 100 MB. I assumed GIN would be heavy because it indexes everything inside the documents, but, really, the lists of row addresses in GIN are stored compressed.
    - **Where the 3732 buffers go:** 2938 table pages (`Heap Blocks: exact=2938`, one for almost every one of the 3022 matching rows, since they are scattered) and 794 index pages.
    - **Estimate was off by 10x, downwards:** `rows=283` in the scan against 3022 actual, both with the seq scan (118 per worker) and with the index. The planner has no statistics about what is inside the `jsonb` documents, so it guesses. It did not change the plan here: the index plan was far cheaper anyway.
    - The first run read everything from disk (`read=43603`); in the second one almost everything was still `read` (43507), because the table (341 MB) does not fit in `shared_buffers`, but the OS cache made it 3x faster (444 -> 136 ms). With the index the second run was all `hit`.
    - **`jsonb_path_ops` operator class** (`CREATE INDEX events_payload_path_idx ON events USING gin (payload jsonb_path_ops);`), same query, tested afterwards:

        | GIN operator class | Plan | Buffers (index + table) | Time, ms | Size |
        |--------------------|------|-------------------------|----------|------|
        | none | Parallel Seq Scan | 43603 | 444 / 136 | – |
        | `jsonb_ops` (default) | Bitmap Heap Scan | 3732 (794 + 2938) | 16.8 / 8.3 | 24 MB |
        | `jsonb_path_ops` | Bitmap Heap Scan | 2942 (4 + 2938) | 2.9 / 2.9 | 14 MB |

        - Same plan, same 2938 table pages, but only 4 index pages instead of 794, so the whole difference is in the index part. The index is also 40% smaller (14 MB against 24 MB), and the query ~3x faster than with the default class (2.9 against 8.3 ms warm).
        - A guess why, not checked: `jsonb_ops` stores keys and values as separate entries, so for this query it has to go through the list for the key `page` (every one of the 3M rows has it) as well as the value `/p/123`; `jsonb_path_ops` stores one entry for the pair `page` + `/p/123` with only the 3022 matching rows in its list.
        - The price: `jsonb_path_ops` supports only containment-like operators (`@>`, `@?`, `@@`), not key-exists ones (`?`, `?|`, `?&`). For a query that only uses `@>`, like this one, it is totally better choice. For the final result I chose the default option due to its versatility.
- **06 (confirmed, one index alone is an extra finding):** My hypothesis was a `Hash Join` of two `Seq Scan`s (probably parallel) with ~50k buffers and a few hundred ms before; indexes on `orders (user_id)` and `order_items (order_id)` created together; after them a `Nested Loop` with `Index Scan`s (or a `Bitmap Heap Scan` for `orders`), a few thousand buffers and 10–30 ms; `order_items` index bigger than the `orders` one. I did not make an assumption about each index size alone, so that part I just measured.
    - **Right:** `Parallel Hash Join` over two `Parallel Seq Scan`s, 48118 buffers (18510 pages of `orders` + 29412 of `order_items`) and 441 ms cold / 140 ms warm; after the indexes a `Nested Loop` with a `Bitmap Heap Scan` on `orders` and an `Index Scan` on `order_items` (`loops=993`), 5966 buffers (8x fewer), 32.6 ms cold / 3.9 ms warm (36x).
    - **Slightly off:** `order_items` has twice the rows of `orders`, but it is only 1.6x the pages (230 MB against 145 MB), because its rows are narrower. The indexes are 18 MB and 64 MB: the `order_items` one is bigger as I expected. If I were to guess before the measurements, I would probably assumed the indexes' size to be a little more than that. But probably it is because a user has many orders with the same `user_id`, and B-tree stores such duplicates compactly (not checked) which results in such a size.
    - **Where the 5966 buffers go:** 973 for `orders` (966 table pages + 7 index pages) and 4993 for the inner `Index Scan`, which runs 993 times, once for each order of the user: about 5 buffers per lookup (3 index levels + ~2 table pages for the ~2 items of an order).
    - **ANALYZE was not needed:** I did not run it, and the estimates were already close (`rows=733` against 993 for `orders`, 1466 against 2014 for the join), the plan was a good one from the start.
    - **Each index alone** (same query, warm run):

        | Indexes | Plan | Buffers | Time, ms |
        |---------|------|---------|----------|
        | none | Parallel Hash Join, 2 Seq Scans | 48118 | 140 |
        | only `order_items (order_id)` | Nested Loop: Parallel Seq Scan on `orders` + Index Scan on `order_items` | 23505 | 29 |
        | only `orders (user_id)` | Hash Join: Bitmap Heap Scan on `orders` + Parallel Seq Scan on `order_items` | 32431 | 110 |
        | both | Nested Loop: Bitmap Heap Scan + Index Scan | 5966 | 3.9 |

    - **Neither index is enough alone:** each one removes only one of the two table scans. With only the `order_items` index the table `orders` is still read in full (~18k pages) to find the 993 orders. With only the `orders` index the join still reads the whole `order_items` (~29k pages) and builds a hash on the other side. The effect of the two together (3.9 ms) is much bigger than of each separately (29 and 110 ms).
    - **The `order_items` index matters more:** the bigger table is the main cost, so it alone gives 29 ms against 110 ms for the other one. Buffers show it only partly (23505 against 32431), the time gap is bigger because the leftover seq scan handles 2M rows of `orders` in one case and 4M rows of `order_items` in the other, while each of them also going through the hash join (not actually measured separately).
    - In the `orders`-only variant the planner chose a `Hash Join` and every one of the 3 processes built its own hash from the `Bitmap Heap Scan` (`loops=3`), so the `orders` part was read 3 times.
- **07 (mostly confirmed, `mcv` vs `dependencies` was unexpected):** My hypothesis was a `Seq Scan` on `users` and a `Hash Join` with a `Parallel Seq Scan` on `orders` under an `Aggregate`; an estimate of ~200 users against ~2000 real (10x under, from multiplying 1/10 by 1/100); the misestimate not changing the plan without an index on `orders (user_id)`, and with that index a `Nested Loop`; `dependencies` fixing the estimate and `mcv` giving the same; a composite index `(country, city)` not fixing it.
    - **Right:** `Finalize Aggregate -> Gather -> Partial Aggregate -> Parallel Hash Join` over two `Parallel Seq Scan`s, 20547 buffers (18511 of `orders` + 1870 of `users` + hits), 68 ms cold / 67 ms warm. The estimate was `rows=217` (= 19987 × 2167 / 200000, exactly the product) against 2006 actual, 9x under. With `orders (user_id)` the plan became a `Nested Loop`, and the extended statistics fixed the estimate to `rows=2160`.
    - **Plan did not change in any variant:** with the wrong (217) and with the right (2160) estimate the planner chose the same plan: `Parallel Hash Join` without the index, `Nested Loop` with it. So in this query the misestimate costs nothing, the time difference (67 → 8.9 ms) comes only from the index. I did not find "the boundary": ~2000 outer rows is still well inside the area where a `Nested Loop` is the cheapest.
    - **Not predicted:** the inner side is an `Index Only Scan` with `Heap Fetches: 0` (autovacuum had already set the visibility map after the seed), so the 2006 lookups cost only 6022 buffers, 3 per lookup.
    - **Another misestimate, not fixed by extended statistics:** the inner side expects `rows=31` orders per user against 10 actual. This is the skew of `user_id` (`random()^3`): the average per distinct value is pulled up by the heavy users. Extended statistics on `users` cannot help with that, so the join estimate is still off (12706 against 9733 per process) but now in the right order of magnitude.
    - **Wrong about `mcv` = `dependencies`:** for `DE` + `DE-3` both are close (`mcv` 1893, `dependencies` 2160, actual 2006), but they differ elsewhere:

        | Query on `users` | No ext. stats | `dependencies` | `mcv` | Actual |
        |------------------|---------------|----------------|-------|--------|
        | `country = 'DE' AND city = 'DE-3'` | 217 | 2160 | 1893 | 2006 |
        | `country = 'DE' AND city = 'FR-3'` (impossible pair) | – | 2100 | 1 | 0 |
        | `country IN ('DE','FR') AND city IN ('DE-3','FR-3')` | – | 4260 | 3840 | 3956 |

        - `dependencies` only stores "city determines country" with a degree (here `{"4 => 3": 1.000000}`), so for any pair it takes the selectivity of the city and ignores the country, even when the pair does not exist. `mcv` stores the real list of (country, city) combinations with their frequencies, so it knows that `DE` + `FR-3` never happens. With 100 combinations the whole list fits into the statistics (2.2 kB against 27 bytes for `dependencies`). With many more combinations than the MCV list can hold, `mcv` would only cover the most common ones, so they make sense together.
    - **Composite index `(country, city)`:** confirmed, the estimate stayed wrong (`rows=197`) and `pg_stats` has no rows for the index. The planner used it (Bitmap Heap Scan, 1233 buffers instead of 1870, index 1416 kB) and the query became faster (5.5 ms), but because of the index, not because of a better estimate. Only expression indexes get their own statistics (03).
    - **`ndistinct`, checked additionally:** it does not change the `WHERE` estimate (`rows=187`), but fixes `GROUP BY country, city`: the estimate of groups went from 1000 (10 × 100) to 100 (actual 100) and the plan changed from `HashAggregate` to `GroupAggregate`. So `dependencies` and `mcv` are for filters, `ndistinct` for grouping and `DISTINCT`.
- **08 (partly confirmed, the stale statistics turned out almost harmless here):** My hypothesis was `rows=1` or close to it before `ANALYZE` and an `Index Scan` over ~400k rows, much slower than a seq scan (like user 1 in the first experiment), then after `ANALYZE` a `Parallel Seq Scan`; and `n_mod_since_analyze = 500000` with an old `last_analyze` in `pg_stat_user_tables`.
    - **Right:** 399756 actual rows; `pg_stat_user_tables` showed `n_mod_since_analyze = 500000`, `last_analyze` from the seed, and `reltuples` was still 2M while the table had 2.5M rows. After `ANALYZE` the estimate became `rows=398931`, almost exact.
    - **Wrong about the estimate:** it was `rows=7893`, not 1 (still 51x under). Without the index the same query was estimated at 104 rows per process (checked in a transaction with `DROP INDEX` + `ROLLBACK`). I think this is because with an index on the column the planner can look up the real maximum value in the index instead of trusting the last histogram bound, so it "sees" that values up to `now() + 5 days` exist, but still assumes they are as rare as one histogram bucket (1% of the rows). The same mechanism showed up in 10 (`orders_pkey` with `idx_scan > 0`).
    - **Wrong about the plan:** `Bitmap Heap Scan`, not `Index Scan`, and it was a good plan: 5978 buffers (4676 table pages + 1302 index pages) and 65.6 / 51.4 ms. The forced `Parallel Seq Scan` read 23183 buffers and took 85 ms. The new rows were inserted together, so they sit in the last 4676 pages of the table one after another (`Heap Blocks: exact=4676`), and a bitmap over them reads only those pages. This is different from user 1 in the first experiment, whose rows were spread over the whole table.
    - **Wrong about the plan after `ANALYZE`:** not a `Parallel Seq Scan` but a `Parallel Bitmap Heap Scan` with the same 5978 buffers, 35.4 / 27.6 ms. So `ANALYZE` fixed the estimate, and the plan only became parallel (~1.9x faster with the same reads).
    - **Takeaway:** the diagnosis "stale statistics" is visible without running the heavy query (`n_mod_since_analyze` is 25% of the table, `reltuples` differs from the real row count) and in the plan (`rows=` 51x below `actual rows=`), and `ANALYZE` is the first thing to do before any new index. But in this case the wrong estimate did not lead to a wrong plan. It would matter more where the estimate decides a join method (not checked).
- **09 (mostly confirmed, write cost was overestimated):** My hypothesis was that `orders_user_id_idx2` (exact copy) and `orders_user_id_idx` (prefix of `(user_id, created_at)`) are redundant and the partial and `status` ones are not; that the catalog query must compare `indpred` and `indexprs` too; sizes ~18 MB each for `(user_id)`, ~60 MB for the composite, a few hundred kB for the partial, ~14 MB for `status`; inserts about 2x slower with all 5 indexes than after dropping two; the partial index almost free to maintain.
    - **Right:** the list of redundant indexes and the sizes: 18 MB, 18 MB, 60 MB, 224 kB, 13 MB (109 MB together). The catalog query (`pg_index` joined to itself on `indrelid`, comparing `indkey`, `indclass`, `indoption`, `pg_get_expr(indexprs)` and `pg_get_expr(indpred)`, and checking that the column list of one index is the start of the other's) returned exactly `orders_user_id_idx2` as an exact duplicate of `orders_user_id_idx`, and both as a left prefix of `orders_user_created_idx`. The same query without the `indpred` comparison flagged `orders_user_pending_idx` three times (as a duplicate of both `(user_id)` indexes and as a prefix of the composite one), so trap 1 is real.
    - **Wrong about the write cost:** `INSERT` of 100k rows (inside `BEGIN ... ROLLBACK`, median of 9 runs, `VACUUM` before each run):

        | Indexes on `orders` | Insert 100k rows, ms (median) |
        |---------------------|-------------------------------|
        | PK only | 89 |
        | PK + 5 (`09_up.sql`) | 372 |
        | PK + 3 (without `idx2` and `user_id_idx`) | 237 |
        | PK + 2 (also without the partial one) | 234 |

        - Dropping the two redundant indexes made the insert 1.6x faster (-36%), not 2x. Each `(user_id)` index costs ~67 ms per 100k rows, almost as much as inserting into the table itself with its PK. With all 5 indexes the insert is 4.2x slower than with the PK only.
        - The partial index: 237 against 234 ms, with overlapping ranges of the 9 runs (229–282 against 228–241), so its maintenance cost is not measurable here. The inserted rows are `completed`, so no entry goes into it, only the predicate is checked. That part of my guess was right.
    - **The caveat about prefix indexes, measured:** with only the composite index left, `count(*)` for user 42 reads 10 buffers instead of 8 and takes 0.16 ms instead of 0.11 ms (both `Index Only Scan`). That is the price of dropping `(user_id)`; here it is small. With the duplicates present the planner simply took one of them (`orders_user_id_idx2`), which shows that the second copy gives nothing.
    - **Measurement trap:** a rolled-back `INSERT` still leaves dead rows in the table and entries in all indexes. In a first attempt without `VACUUM` between runs every run was slower than the previous one and the `(user_id)` indexes grew from 18 to 19 MB. So the sizes above were taken before the insert runs, `VACUUM` runs before every insert, and the series starts after `VACUUM FULL orders`.
- **10 (partly confirmed, missed the primary keys):** My hypothesis was `orders_user_id_idx` with `idx_scan > 0`, `orders_total_idx` with `idx_scan = 0`, and an answer "can be dropped, but with caveats" (short statistics period, monthly reports, replicas); and ~40 MB for the `total` index.

- **11 (mostly confirmed, the forced plan was not what I expected):** My hypothesis was a `Seq Scan`, probably parallel, ~18.5k buffers and a few hundred ms; the planner ignoring a `(created_at)` index; the forced plan being an `Index Scan` with hundreds of thousands to a million buffers and several times slower; a ~40 MB index; HypoPG not choosing it either.

    - **Wrong about the forced plan:** with `enable_seqscan = off` the planner chose a `Bitmap Heap Scan`, not an `Index Scan`. It reads every table page once (`Heap Blocks: exact=18511`) plus 2734 index pages: 21245 buffers, 15% more than the seq scan. And it was faster in time: 140 / 134 ms against 215 / 209 ms; with `TIMING OFF` in alternating runs 94–103 against 184–185 ms, after a restart 112–114 against 184–186 ms, so ~1.8x. A guess, not checked: both read the whole table, but the bitmap scan checks only the 1M tuples from the index, while the seq scan checks all 2M and filters out half, so the difference is CPU.

- **12 (partly confirmed, `work_mem` made the query slower, and the index made it worse):** My hypothesis was `Gather Merge` with a parallel `external merge`, ~50–60 MB of temp and ~1 s; 16 and 64 MB still on disk (or 64 MB already enough), 256 MB in memory and about 2x faster; the planner not using an index on `(total)` for a full sort.
    - **Right:** `Gather Merge -> Sort (external merge) -> Parallel Seq Scan`, every process spilled ~21–22 MB, 8103 temp pages written in total (~63 MB). Time was lower than I thought: 592 / 585 ms with per-row timing and ~0.50 s with `TIMING OFF`.
    - **Wrong about where it switches:** with 64 MB and even 120 MB the sort still went to disk, `quicksort` started at 124 MB (`Memory: 125741kB`). The in-memory sort needs ~124 MB for data that took ~63 MB on disk, about 2x. I guess the in-memory tuples carry more overhead than the compact format written to temp files.
    - **Wrong about the speedup:**

        | `work_mem` | Plan | Sort Method | Time, ms (`TIMING OFF`, 3 runs) |
        |------------|------|-------------|---------------------------------|
        | 4 MB (default) | Gather Merge, 3 processes | external merge, ~21 MB each | 499–506 |
        | 8–16 MB | serial Sort | external merge, 63 MB | 743–763 |
        | 32–120 MB | serial Sort | external merge, 63 MB | 810–918 |
        | 124–256 MB | serial Sort | quicksort, ~124 MB | 687–701 |
        | 256 MB, parallel forced | Gather Merge, 3 processes | quicksort, ~50 MB each | 509–511 |
        | 4 MB, no parallel | serial Sort | external merge, 63 MB | 914–918 |

        - From 8 MB on the planner dropped the parallel plan, so raising `work_mem` made the query slower overall: 0.50 s → 0.69 s even with the sort fully in memory.
        - The effect of the spill itself is visible only when the plan shape is the same: serial 0.92 s on disk against 0.69 s in memory (1.3x), parallel 0.50 s on disk against 0.51 s in memory (no difference). The temp files stayed in the OS cache, so "Disk" here cost little.
        - A bigger `work_mem` that is still too small made the external merge slower, not faster (743 ms at 8–16 MB, 913–918 ms at 120 MB). Not checked why.
    - **Wrong about the index:** with `orders (total)` (43 MB) the planner **chose** the `Index Scan` by itself (cost 126020 against 321345 for `Gather Merge` + `Sort`), and it was ~2x slower: 1118 / 1125 ms (1023–1032 with `TIMING OFF`) and 2003322 buffers (one per row, `correlation` of `total` is ~0). With `SET effective_cache_size = '64MB'` the planner went back to `Sort`. So, I think, with the default 4 GB it assumes the 145 MB table stays in cache and random reads are cheap. Here the index is harmful for the full sort, and only useful for `ORDER BY total LIMIT 100` (0.33 ms, 103 buffers).
    - **Takeaway:** `external merge` in a plan is a sign, not a diagnosis by itself: here the parallel plan with a spill was the fastest variant of all. If `work_mem` is the answer, it is `SET work_mem` for this session or query (`SET LOCAL` inside a transaction, or `ALTER ROLE ... SET work_mem` for a reporting role), never globally: `work_mem` is per sort or hash node, per process, so a parallel plan with 3 processes can take 3x of it, and 100 connections with such queries would need tens of GB. And the change has to be checked against the plan shape, not only against `Sort Method`. The bigger win would come from not sorting 2M rows at all (`LIMIT`, pagination), not from memory.
